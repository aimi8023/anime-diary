# 版本化备份与恢复设计

日期：2026-07-29

## 背景

Anime Diary 是个人长期维护、公开只读展示、仅站长管理的追番记录站点。Bangumi 辅助录入已经降低了添加记录的成本，接下来需要优先确保不断积累的数据不会因误删、错误编辑、导入失误、并发覆盖或存储异常而丢失。

当前生产环境将全部记录作为一个数组保存在 Upstash Redis 的 `anime:all` 键中，本地开发则写入 `data/anime.json`。管理页已有浏览器端 JSON 导出，但没有导入、历史版本、一键恢复或服务端备份。现有 Redis 写入采用“读取整个数组、在应用内修改、整体覆盖”的方式；两个写请求重叠时，较晚提交的旧副本可能覆盖另一个请求的修改。

本阶段采用“先简单、以后可扩展外部备份”的方向：第一版不增加新服务，每次数据变更前在当前存储中创建版本快照，同时保留可下载的 JSON 作为独立副本。存储边界为未来接入对象存储、私有代码仓库或其他外部位置预留扩展点。

## 目标

- 在每次添加、编辑、删除、导入和恢复前自动保存当前完整数据。
- 保留最近 30 个快照，并自动清理更早的版本。
- 在管理页查看快照时间、触发原因和记录数量。
- 比较任意快照与当前数据的新增、移除和修改数量。
- 下载当前数据或任意历史快照。
- 校验并导入现有 JSON 导出文件或新版带元数据的备份文件。
- 恢复任意历史快照，并在恢复前再次备份当前状态。
- 避免并发读改写导致静默覆盖。
- Redis 故障或数据解析失败时明确报错，不把异常伪装成空列表。
- 保持 Redis 和本地 JSON 两种存储实现的行为一致。

## 非目标

- 第一版不接入 GitHub、Google Drive、S3 或其他外部备份服务。
- 不增加 Vercel Cron 或其他定时任务。
- 不记录每个字段的逐项修改历史。
- 不提供单条记录级别的撤销或回收站。
- 不自动合并两个备份文件。
- 不增加多用户、注册、多租户或面向公开访客的备份能力。
- 不修改 Bangumi 数据获取与辅助录入规则。

## 总体架构

备份能力分为三层：

```text
管理页
  └─ /api/backups/*
       ├─ BackupService
       │    ├─ 列表、比较、导入校验、恢复编排
       │    └─ 统一错误与结果结构
       └─ VersionedAnimeStorage
            ├─ Redis 实现：版本检查与原子写入
            └─ JSON 实现：进程内串行化与临时文件替换
```

业务 API 不再分别调用 `getAll()` 后自行执行读改写，而是通过版本化存储操作完成“读取当前状态、生成快照、写入新状态”。这样添加、编辑、删除、导入和恢复共享同一套安全写入语义。

备份服务依赖抽象接口，不直接依赖 Redis 键或本地目录。未来增加外部备份时，可以新增适配器或在成功写入后触发异步复制，不需要重做管理页、导入校验和恢复流程。

## 数据模型

### 快照

```ts
type BackupReason = "add" | "update" | "delete" | "import" | "restore";

interface BackupSnapshot {
  id: string;
  createdAt: string;
  reason: BackupReason;
  recordCount: number;
  schemaVersion: 1;
  data: Anime[];
}
```

- `id` 使用不可预测的唯一 ID。
- `createdAt` 使用服务端 UTC ISO 时间。
- `reason` 只记录触发类型，不保存密码、令牌、请求头或完整请求体。
- `recordCount` 是快照创建时的记录数，便于列表展示。
- `schemaVersion` 用于将来迁移备份格式。
- `data` 是变更前的完整、已校验记录。

### 当前状态与并发版本

存储层维护单调递增的版本号：

```ts
interface AnimeState {
  revision: number;
  data: Anime[];
}
```

所有写操作携带读取时的 `revision`。只有当前版本仍匹配时才允许创建快照并写入新数据；不匹配说明期间已有其他写入，调用方需要重新读取、重新应用操作并有限重试。

现有 Redis `anime:all` 数组与本地 `data/anime.json` 均视为 `revision = 0` 的旧格式。首次成功写入时建立新的版本化状态，不要求部署前手动转换数据。

## Redis 键设计

- `anime:state`：包含当前记录与版本号的 `AnimeState`，作为新版权威状态。
- `anime:all`：部署前已有的旧数组键，仅用于兼容迁移；新版状态建立后不再作为权威数据。
- `anime:backups`：以创建时间为分数的有序快照索引。
- `anime:backup:metadata`：以快照 ID 为字段的元数据哈希。
- `anime:backup:{id}`：单个快照的完整记录数据。

把版本号和当前数据放在同一个状态对象中，避免两个键在异常情况下出现版本与内容不同步。索引成员只保存快照 ID，元数据与完整数据分开保存，避免读取列表时加载全部历史记录。列表接口读取索引和元数据哈希；详情、下载或恢复时才读取完整快照。

## 安全写入流程

### Redis

每次添加、编辑、删除、导入或恢复执行以下流程：

1. 读取当前数据和版本号。
2. 服务端验证请求，并基于最新状态计算下一状态。
3. 执行 Lua 脚本，在同一原子区间内：
   - 比较当前版本与期望版本；
   - 保存变更前数据与快照元数据；
   - 更新快照索引；
   - 以一次 `SET` 写入同时包含下一版本号与数据的 `AnimeState`。
4. 如果版本不匹配，重新读取并重新应用操作，最多重试有限次数。
5. 重试后仍冲突，返回明确的并发冲突错误，要求管理页刷新后重试。
6. 核心写入成功后，执行幂等的保留策略清理，删除超过 30 个的最早快照、元数据与索引项。

脚本参数在执行前完成校验，命令顺序遵循“先保证旧数据可恢复，再替换当前数据”。清理旧快照不属于核心原子写入；即使清理暂时失败，也只会多保留历史版本。后续列表读取或下一次写入可以再次触发清理。

Lua 用于解决依赖读取结果的条件写入。普通 pipeline 不能防止其他客户端命令穿插；单纯 `MULTI/EXEC` 虽能原子执行已排队命令，却不能根据事务中刚读取到的值决定是否继续写入。

### 本地 JSON

本地实现提供相同语义：

1. 使用进程内写入队列串行处理修改。
2. 读取并验证 `data/anime.json`。
3. 将旧数据写入 `data/backups/{timestamp}-{id}.json`。
4. 将新数据写入同目录临时文件。
5. 完整写入并刷新成功后，用原子重命名替换当前文件。
6. 清理超过 30 个的最早备份。

本地目录主要用于开发。生产环境不依赖部署文件系统保存持久备份。

## 变更操作语义

### 添加

- 在最新状态中执行 Bangumi ID 重复检测。
- 生成新记录后，通过安全写入流程保存。
- 快照原因为 `add`。

### 编辑

- 在最新状态中重新查找目标 ID。
- 重新执行字段和 Bangumi ID 冲突校验。
- 快照原因为 `update`。

### 删除

- 在最新状态中确认目标仍存在。
- 快照创建成功后才删除。
- 快照原因为 `delete`。

### 导入

- 导入是完整替换，不做隐式合并。
- 应用时必须重新校验文件，不信任此前的浏览器预览。
- 快照原因为 `import`。

### 恢复

- 读取并验证目标快照。
- 将恢复前的当前状态先保存为新快照。
- 将目标快照数据写为新的当前状态；原历史快照保持不变。
- 快照原因为 `restore`。

因此恢复操作本身可逆：如果恢复错了时间点，可以从刚生成的 `restore` 快照回到恢复前状态。

## 备份格式

新版下载文件使用以下包装格式：

```ts
interface AnimeBackupFile {
  format: "anime-diary-backup";
  schemaVersion: 1;
  exportedAt: string;
  source: "current" | "snapshot";
  snapshot?: {
    id: string;
    createdAt: string;
    reason: BackupReason;
  };
  data: Anime[];
}
```

导入同时兼容：

- 现有管理页导出的裸 `Anime[]` 数组。
- 新版 `AnimeBackupFile`。

导出不包含管理员密码、Cookie、Redis 地址、Redis Token、Bangumi Token 或其他环境变量。

## 导入校验

导入文件第一版最大 5 MB，必须能解析为 JSON。服务端校验：

- 顶层结构是裸数组或支持的备份包装格式。
- `schemaVersion` 是受支持版本。
- 每条记录包含合法的 `id`、`title`、`season`、`rating`、`episodes`、`tags` 和 `createdAt`。
- 可选 Bangumi 字段类型正确。
- 记录 ID 不重复。
- `bangumiId` 不重复。
- 数值范围与现有创建、编辑 API 一致。
- 字符串和数组设定合理长度上限，避免异常大字段绕过文件总量限制。

校验失败返回按记录定位的问题列表，不写入任何数据。文件内容不会写入服务端日志。

空数组是合法备份，但应用前需要额外明确确认，避免选错文件后意外清空记录。

## 差异计算

预览和恢复确认页将目标数据与当前数据按记录 `id` 比较：

- 当前没有、目标存在：新增。
- 当前存在、目标没有：移除。
- 两侧均存在但规范化字段内容不同：修改。

结果包含新增、移除、修改和未变化数量。第一版只展示计数与少量代表性标题，不实现逐字段可视化 diff。Bangumi ID 仅用于导入重复校验，不作为自动合并依据。

## 管理页交互

管理页增加可折叠的“备份与恢复”区域，与日常添加表单和记录列表分开。

### 状态摘要

显示：

- 当前记录数。
- 最近一次自动快照时间。
- 当前已保留快照数量。
- “下载当前数据”和“导入 JSON”入口。
- 同存储快照的限制提示，以及定期下载独立副本的建议。

### 快照列表

每项显示：

- 快照时间。
- 触发原因的中文描述。
- 快照内记录数量。
- “查看差异”“下载”“恢复”操作。

### 恢复

1. 点击恢复后加载目标快照并计算差异。
2. 弹窗显示目标时间、记录数和新增/移除/修改数量。
3. 用户确认后发起恢复。
4. 按钮在请求期间禁用，避免重复提交。
5. 成功后刷新当前记录与快照列表，并提示恢复到的时间点。

### 导入

1. 用户选择本地 JSON 文件。
2. 浏览器检查扩展名与大小，服务端执行权威校验。
3. 页面展示文件元数据、记录数、警告、错误和差异摘要。
4. 存在错误时禁止应用。
5. 若目标为空，显示额外确认。
6. 用户确认后重新上传并由服务端再次校验、备份和完整替换。

管理页不把预览结果当作授权令牌或最终数据，避免预览后文件内容变化造成校验绕过。

## 站内 API

所有接口均返回结构化 JSON 错误；下载接口除外。

### `GET /api/backups`

- 返回快照元数据列表，不包含完整 `data`。
- 默认按时间倒序。

### `GET /api/backups/:id`

- 默认返回快照元数据和相对当前状态的差异摘要。
- 使用明确的下载参数或独立响应模式下载备份文件。
- 不存在返回 `404`。

### `POST /api/backups/:id/restore`

- 校验快照 ID。
- 重新读取目标快照和最新当前状态。
- 恢复前创建当前状态快照。
- 成功返回新版本号、当前记录数与所恢复快照信息。

### `POST /api/backups/import/preview`

- 接收最大 5 MB 的 JSON 文件。
- 返回文件元数据、校验问题和差异摘要。
- 不写入当前数据或快照。

### `POST /api/backups/import/apply`

- 再次接收并完整校验文件。
- 空数组要求显式确认字段。
- 校验通过后创建当前状态快照并完整替换。

### 当前数据下载

现有浏览器端导出改为服务端生成新版备份文件，确保导出的是服务端最新状态，而不是可能过期的页面内存。

## 权限与安全

- `/api/backups/:path*` 加入 `proxy.ts` 的管理员保护范围。
- 所有备份接口，包括只读列表与下载，都只允许已登录管理员访问。
- 修改类请求校验同源 `Origin`；无法证明同源时拒绝。
- 管理员 Cookie 继续使用 `httpOnly`、生产环境 `secure` 和 `sameSite=lax`。
- 文件名由服务端生成，不接受用户提供的文件路径。
- 本地备份 ID 和文件名经过约束，不允许目录穿越。
- 服务端错误不回传 Redis 键、文件绝对路径、脚本内容或凭据。
- 公开首页和公开 `/api/anime` GET 不暴露备份元数据。

## 错误处理

- Redis 不可访问、JSON 解析失败或当前状态结构非法时返回服务错误，不回退为空数组。
- 自动快照失败时终止原变更。
- 快照清理失败可以记录告警并暂时多保留版本，但不能删除仍在索引中的错误目标。
- 导入预览失败保留已选择文件信息和错误提示，不影响当前记录。
- 恢复或导入失败时刷新当前状态，确认页面与服务端一致。
- 并发冲突有限重试；超过次数后返回 `409`。
- 不存在的目标记录、快照或已被其他请求修改的对象使用明确状态码与中文提示。
- 客户端只在服务端确认成功后显示成功状态。

## 保留策略

- 每次受保护的变更生成一个快照。
- 默认保留最近 30 个。
- 计数按完成创建时间排序，不按业务季度或记录创建时间排序。
- 恢复不会删除被恢复的目标快照。
- 第一版不提供手动固定某个快照，所有快照遵循相同保留策略。
- 下载到用户设备的文件不受站内保留策略影响。

30 个完整数组对当前个人数据规模足够简单且成本可控。若未来记录或快照体积明显增长，可保持 API 不变，改为压缩对象、增量快照或外部对象存储。

## 可扩展性

备份服务与具体存储实现之间保留明确边界：

```ts
interface BackupRepository {
  list(): Promise<BackupMetadata[]>;
  get(id: string): Promise<BackupSnapshot | null>;
  save(snapshot: BackupSnapshot): Promise<void>;
  prune(keep: number): Promise<void>;
}
```

第一版 Redis 与 JSON 版本化写入仍需在各自存储内部协调快照和当前状态，以保证操作顺序与并发安全；该接口主要约束读取、下载与未来复制能力。将来增加外部存储时，可以在站内写入成功后复制快照，并额外展示复制状态，而不改变备份文件格式和恢复交互。

## 测试与验收

### 单元测试

- 新旧两种导入格式均可解析。
- 非法 JSON、未知格式版本和超限文件被拒绝。
- 必填字段、数值范围、重复 ID 与重复 Bangumi ID 校验。
- 差异统计覆盖新增、移除、修改和未变化。
- 空数组需要额外确认。
- 快照元数据和下载格式不泄露敏感配置。

### 存储测试

- 添加、编辑、删除前均创建正确快照。
- 导入与恢复前创建当前状态快照。
- 恢复后可通过新快照回到恢复前状态。
- 只保留最近 30 个快照。
- 版本冲突不会覆盖较新的写入。
- 冲突可重试，超过限制返回明确错误。
- 当前状态或旧格式数据损坏不会被解释为空数组。
- Redis 与 JSON 实现满足同一行为契约。
- 本地写入失败不会留下半写入的当前 JSON。

### API 测试

- 未登录访问列表、详情、下载、导入和恢复均被拒绝。
- 非同源修改请求被拒绝。
- 列表不返回完整快照数据。
- 不存在的快照返回 `404`。
- 预览不产生写入。
- 应用导入时再次执行服务端校验。
- 恢复成功返回新的当前状态摘要。
- Redis 故障返回服务错误而不是空列表。

### 交互验收

- 完成一次“修改记录 → 查看自动快照 → 比较差异 → 恢复”。
- 完成一次“下载当前数据 → 导入预览 → 应用导入”。
- 恢复前状态可再次恢复。
- 导入错误文件不会改变当前数据。
- 空数组导入具有额外确认。
- 桌面端与移动端均可完成下载、导入和恢复。
- 最终运行 lint、类型检查、自动化测试和生产构建。

## 发布与兼容

- 现有记录无需人工迁移。
- 读取时优先使用 `anime:state`；不存在时才读取旧 `anime:all` 并视作版本 0。首次成功写入通过原子脚本建立 `anime:state`，旧键暂时保留但不再参与新版读取。
- 本地 JSON 继续保存裸数组，并在同目录维护版本元数据；首次写入建立缺失的版本信息。
- 新接口与管理 UI 同一版本发布，避免出现只有恢复按钮但存储层不支持的状态。
- 发布后先执行一次当前数据下载，作为站外基线副本。
- Vercel 与 Upstash 环境变量沿用现有配置，不增加第一版必需变量。

## 已知限制

- 自动快照与当前数据仍位于同一 Upstash 数据库，无法抵御整个数据库、账号或供应商级故障。
- 本地开发备份不等于生产备份。
