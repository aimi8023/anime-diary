# Anime Diary 开发历程

本文只保留项目演进中的关键问题、交付结果和长期决策。完整逐步实施记录已从工作树移除，但仍可通过 Git 历史查看。

## 项目基础：公开展示与单人管理

**时间：** 2026-06-06 至 2026-06-10

项目从个人追番页面演进为可部署的 Next.js 应用，确定了长期定位：公开展示记录，只有站长本人管理。

完成内容：

- 建立季度记录、评分、感想和管理后台；
- 支持本地 JSON 与 Redis 两种存储；
- 上线 Vercel 并处理多种 Upstash/KV 环境变量；
- 加入标签和后台记录搜索；
- 提供第一版数据导出能力。

长期决策：不引入多用户账户和追番状态流转，记录本身就是站长选择展示的作品。

代表提交：`f86545a`、`9ff2b47`、`ded8225`。

## 阶段一：Bangumi 辅助录入

**时间：** 2026-07-29

### 问题

手动填写标题、封面、季度、话数和标签成本高，容易出现格式不一致；但全量同步 Bangumi 又不符合“只收录自己看过作品”的需求。

### 结果

- 管理员按需搜索动画条目；
- 选择条目后预填标题、原名、封面、首播日期、季度和话数；
- Bangumi 标签只作为候选，由管理员点击选择；
- 保存 `bangumiId` 和来源链接，提供精确重复检测；
- Bangumi 不可用时仍可手动填写。

### 长期决策

Bangumi 是录入助手，不是本站权威数据源。个人评分、标签和感想由站长决定，保存后公开页面只读取本站快照。

代表提交：`3c1ba1c`、`e038ffa`、`1201833`、`8e794d3`。

## 阶段二：服务端优先的公开档案

**时间：** 2026-07-29 至 2026-07-30

### 问题

旧首页通过客户端重复请求数据，首屏需要等待；记录增加后，查找、筛选和回顾效率不足，年份展开还出现过页面加载错误。

### 结果

- `app/page.tsx` 在服务端只读取一次记录并直接渲染首屏；
- 建立关键词、年份、季度、标签、最低评分和排序的纯函数核心；
- 筛选条件同步到 URL，可刷新、分享和浏览器前进后退；
- 按年份与季度折叠，最新年份默认展开；
- 区分真正空档案、无筛选结果和存储读取失败；
- 保留公开 `GET /api/anime` 的兼容性，但首页不再调用它。

### 长期决策

数据由 Server Component 注入，客户端只做交互和派生计算；筛选、排序、分组和统计集中在 `lib/archive/`，不建立重复的全局番剧数据状态。

代表提交：`999991c`、`6cb6993`、`4efd103`、`0cde405`、`7553411`。

## 阶段三：版本化备份与恢复

**时间：** 2026-07-29

### 问题

单份 Redis/JSON 数据无法可靠抵御误删、错误编辑和导入失误；浏览器端导出也不足以提供历史恢复和并发写保护。

### 结果

- 添加、编辑、删除、导入和恢复前自动保存快照；
- 使用 `revision` 和条件提交避免并发旧副本覆盖新数据；
- Redis 原子写入当前状态、旧数据快照和索引；
- 本地 JSON 实现相同行为契约；
- 管理后台支持备份列表、差异预览、JSON 导入导出和一键恢复；
- 默认保留最近 30 个版本；
- 恢复前再次备份当前数据，保持操作可逆；
- 兼容旧数组备份和新版带元数据格式。

### 长期决策

备份服务依赖存储接口，不把 Redis 键泄漏到 UI。第一阶段使用同一存储保存版本，同时保留下载 JSON 的站外出口；未来可增加对象存储副本而不改变导入恢复流程。

代表提交：`c71fb74`、`37bfda7`、`d794685`、`e1f83e3`、`01de0f4`、`1f25b22`。

## 阶段四：管理后台信息架构

**时间：** 2026-07-30

### 问题

记录列表、添加表单和备份操作同时出现在一个长页面中，日常维护容易受到无关信息干扰，后台首次进入还会请求并不需要的备份数据。

### 结果

- 后台拆分为“记录”“添加/编辑”“备份恢复”三个互斥工作区；
- 日常进入默认聚焦记录维护；
- 备份管理只在对应工作区挂载并请求数据；
- 添加、编辑、取消和保存后的返回路径统一；
- 记录搜索和列表使用页面自然滚动。

### 长期决策

后台继续使用页面局部状态，不引入全局状态库。工作区之间以清晰组件接口协作，各自负责自己的加载、空状态和错误反馈。

代表提交：`b0e58d6`、`33cabdd`、`2829373`、`524e79e`。

## 阶段五：共享校验与安全边界

**时间：** 2026-07-30

### 问题

新增和编辑曾存在重复且不一致的字段处理；写接口主要依赖 Cookie 和路由守卫，错误反馈也分散在各组件中。

### 结果

- 创建和更新共享 `lib/anime/validation.ts`；
- API 统一安全错误结构和客户端错误读取；
- 所有管理写操作要求严格同源 `Origin`；
- 登录失败按客户端限流：15 分钟内 5 次失败后暂时拒绝；
- Redis 可用时跨实例共享计数，否则回退到单进程内存；
- 客户端标识只以 SHA-256 摘要进入 Redis；
- 管理界面使用统一可访问的行内反馈。

### 长期决策

`proxy.ts` 负责认证粗边界，每个写路由仍显式执行同源检查和输入校验。服务端错误不得回传凭据、内部路径或底层存储细节。

代表提交：`065851e`、`71d9275`、`ba53b7e`、`2d04125`、`4058924`。

## 阶段六：“水光档案”视觉系统

**时间：** 2026-07-30

### 问题

公开页、登录和后台的颜色、表面、按钮、焦点和动效缺少统一规则，背景插画有时会与正文竞争。

### 结果

- 在 `app/globals.css` 建立画布、表面、文字、状态、阴影、圆角和动效令牌；
- 统一面板、字段、按钮、标签、焦点和状态语义类；
- 公开档案、登录页和后台迁移到同一视觉语言；
- 公开封面统一为 2:3；
- 外部图片迁移到 `next/image` 的 `unoptimized` 模式；
- 全局与 Framer Motion 动效遵守减少动态偏好；
- 强化键盘焦点、44px 操作区域和非颜色状态提示。

### 长期决策

背景只负责氛围，文字对比度由稳定表面保证。业务组件消费语义类，不在局部复制新的一组颜色、阴影和焦点规则。

代表提交：`ce52dd2`、`fb7e52b`、`da3b0b1`、`1b98a89`、`6c6a621`。

## 阶段七：紧凑档案、导航搜索与沉浸式详情

**时间：** 2026-07-30

### 问题

完整筛选表单长期占据首页开头，卡片同时展示过多信息导致密度偏低，右侧窄详情抽屉也不适合长标题、标签和感想。

### 结果

- 搜索成为导航栏按钮，显示活动筛选数量；
- 桌面端打开居中搜索卡片，手机端打开底部抽屉；
- 首页卡片只保留封面、评分、季度和标题；
- 网格提升为 2/3/4/6/7 列；
- 桌面详情改为约 960px 的封面/内容双栏；
- 手机详情改为近全屏抽屉；
- 保留遮罩和 Escape 关闭、滚动锁、焦点恢复和减少动态；
- 用 `Suspense` 隔离导航中的 URL 参数读取，保证静态错误页生产构建。

### 长期决策

首页首先服务“浏览”，完整信息进入详情层；搜索面板只控制显示，筛选状态仍由 `ArchiveBrowser` 和 URL 持有。

代表提交：`1ac8b03`、`7cd5354`、`0c55b37`、`70e95c2`、`82470bb`。

## 阶段八：海报墙网格与季度批量入库

**时间：** 2026-08-30

### 问题

横向滚动行在每组内容稀少（每季 1–3 部）时体验差、交互负担重，也隐藏内容；每季度约十部、加上大量积压的过往季度，逐部搜索入库过于繁琐。

### 结果

- 首页横向滚动行改为自适应海报墙网格，全部作品直接可见、纵向滚动；`ScrollRow` 仅保留在年度抽屉；
- 分组标题保持纯文字，不添加底色盒子或吸顶处理；
- 评分维度下卡片补充季度标签，同分档内按播出档期排序；
- 新增"季度批量"录入模式：按年份+季度分页拉取 Bangumi 放送列表（单页上限 20，至多 5 页 100 部，按热度），勾选后一键入库；
- `rating 0` 作为"未评分"哨兵值：批量入库默认未评分，之后经记录工作区"补评分"对话框补填；公开页如实显示"未评分"，均分与年度之作统计排除；
- Bangumi 客户端支持可选出站代理（`BANGUMI_PROXY` / `HTTPS_PROXY`），解决部分本地网络直连超时（DNS 污染）；
- 季度划分校准为 春=12/1/2 月、夏=3–5 月、秋=6–8 月、冬=9–11 月，12 月首播归次年春；拉取区间与存储推导共用同一划分。

### 长期决策

档案站优先"一眼看全"，横向交互只留在年度抽屉；录入效率不牺牲数据真实性——评分与感想始终由管理员亲自填写，未评分是显式状态而非占位分数。

## 候选列表滚动优化

**时间：** 2026-08-31

### 问题

季度批量候选列表滚动明显卡顿。排查确认并非滚动触发重复查询（点击获取后只请求一次），而是绘制成本：上百张卡片一次性挂载、常驻界面（头部/底栏/面板）大量使用 `backdrop-filter`、body 上 `background-attachment: fixed` 的全屏背景加固定渐变层使每一帧滚动都要重绘整个视口。

### 结果

- 候选列表改为分页展示，每页 24 部（大屏 8 列正好 3 行），翻页不重新请求，跨页保持选中；一次拉取至多 144 部，列表缓存延长到 10 分钟；
- 候选卡片改显示压缩缩略图（`common`），入库仍保存全尺寸封面（`large`），降低滚动时新封面的下载与解码开销；
- 移除头部、底栏、返回顶部、滚动箭头与卡片角标等常驻元素的 `backdrop-filter`，用更高不透明度的底色补偿观感；弹层类模糊仅在打开时存在，予以保留；
- 全屏背景图与渐变迁入 `position: fixed` 伪元素，并以 `transform: translateZ(0)` 提升为独立合成层，滚动交由合成器处理，主线程不再逐帧重绘背景。

### 长期决策

滚动性能优先选择对合成器友好的分层：固定背景独立提层，常驻界面避免实时模糊，模糊只留给模态与抽屉等瞬时遮罩。
